# OEM automation and hardware coverage boundaries

- Samsung Odin: the current path performs bounded Windows UI Automation against the selected Odin process and its accessible controls. It verifies the selected COM port and visible package fields, requires compatibility/backup confirmation and uses one accessibility Invoke on Start. It does not reverse engineer Download Mode or implement undocumented Samsung transport commands. Real-device Hardware-in-the-Loop verification is still needed across supported Odin/device variants.
- Qualcomm QDL: the existing workflow supports device/USB discovery, QDL list and chip-info, Firehose/XML package inspection, dry-run and guarded execution with the OEM-supplied programmer. It does not defeat DAA, Secure Boot, OEM authorization or programmer policy. Actual board-level authorization and HIL testing remain necessary.
- MediaTek DA: the existing workflow inspects Scatter/images/DA/Auth artifacts and hands off to the official SP Flash Tool provided by the technician. It deliberately does not ship a generic DA or automate BROM/DAA/SLA bypass. A signed/authorized DA and exact model/board entitlement are required.
- Xiaomi Fastboot: the existing flow reads device variables and inspects ROM packages; the constrained IMG writer uses exact serial/product checks and requires an already-unlocked bootloader, approved partition and package/backup confirmation. It does not unlock the bootloader or bypass Xiaomi account authentication.
- Brand-private protocols: remain Planned until an OEM publishes or supplies a licensed SDK/protocol, model-specific signed components and test hardware. Invented packets or unverified commands are not a substitute for vendor support.
- Native Plugin DLL runtime: remains Planned. Existing plugins are signed packages and allow-listed data-only JSON workflows. Loading arbitrary DLLs in the main SoftBox process is not isolation; a restricted host process, IPC policy, job/resource limits, publisher policy and security tests are required before this can be enabled.
- Board Maps: the bundled generic-android.json remains an educational exploded view, not a model-specific PCB map. The importer rejects maps without exact model/device-code matching, source URL, verifier metadata, revision compatibility and valid part geometry. No board coordinates or component placement are invented; licensed OEM/service schematics or verified boardview data must be supplied for each exact model/board revision.
